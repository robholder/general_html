Cron

Crontab Reference Guide

A cron job is a scheduled task executed by the Unix/Linux cron daemon at specified intervals. Crontab (cron table) is the configuration file used to manage these schedules.

1. Crontab Field Structure Diagram

A cron schedule consists of five time-and-date fields followed by the command to execute: 

 ┌───────────── minute (0 - 59)
 │ ┌───────────── hour (0 - 23)
 │ │ ┌───────────── day of the month (1 - 31)
 │ │ │ ┌───────────── month (1 - 12) or JAN-DEC
 │ │ │ │ ┌───────────── day of the week (0 - 6) or SUN-SAT (0 or 7 is Sunday)
 │ │ │ │ │
 * * * * * /path/to/command [arguments]

2. Special Characters Reference

  • * (Asterisk): Matches any value or acts as a wild card ("every").
  • , (Comma): Specifies a list of values (e.g., 1,3,5 for hours 1, 3, and 5).
  • - (Hyphen): Defines a range of values (e.g., 1-5 for Monday through Friday).
  • / (Slash): Specifies step values or increments (e.g., */15 in the minute field means "every 15 minutes").

3. How to Manage Crontab Jobs

Editing and Viewing

  • Edit/Create crontab for current user: 
crontab -e
  • List current user's cron jobs: 
crontab -l
  • Remove all cron jobs for current user: 
crontab -r

4. Practical Examples

Crontab Syntax Description
0 3 * * * Run every day at 3:00 AM.
*/10 * * * * Run every 10 minutes.
0 0 1 * * Run at midnight on the 1st day of every month.
30 2 * * 1 Run every Monday at 2:30 AM.
0 9-17 * * 1-5 Run every hour on the hour between 9 AM and 5 PM, Monday through Friday.

5. Helpful Best Practices

  • Use Absolute Paths: Cron runs in a minimal environment with a limited PATH. Always use full paths for binaries and scripts (e.g., /usr/bin/python3 /home/user/script.py).
  • Redirect Output: To prevent cron from emailing output (or clogging system logs), explicitly redirect standard output and errors: 
0 2 * * * /path/to/script.sh >/dev/null 2>&1

Cron with Find

Combining cron with the find command is the standard, most reliable way to automatically clean up old backups without having to write a custom script.

Here is how you can set it up.

1. The Core Command

The find utility is built into almost all Unix/Linux systems and is perfect for this. To find and delete files older than a certain number of days, you can use: 

find /path/to/backup -type f -mtime +30 -delete

Breakdown of the flags:

  • /path/to/backup: The target directory you want to clean.
  • -type f: Target files only (leaves directories alone).
  • -mtime +30: Matches files modified more than 30 days ago. (Change 30 to whatever number of days you prefer).
  • -delete: Removes the matched files safely. *(Tip: Test your command first by replacing -delete with -print to see a list of files it's about to delete!)*

2. Setting Up the Crontab Job

To make this run automatically on a schedule, you will add it to your user's crontab.

  • Open your terminal and open the cron editor: 
crontab -e
  • Add a line defining when you want it to run and the command. For example, to run this cleanup every day at 2:00 AM, add this line: 
0 2 * * * find /path/to/your/backup -type f -mtime +30 -delete >/dev/null 2>&1

(Note: >/dev/null 2>&1 at the end silences cron from emailing you output every time it runs, unless an error occurs).

⚠️ A Crucial Cron Tip

Cron runs in a minimal environment, meaning it often doesn't load your standard shell profile or custom path variables. Always use absolute paths (like /usr/bin/find instead of just find, and /home/username/backups instead of ~/backups). You can find your exact path to find by running which find in your terminal.

On my current Redhat Enterprise environment: 

/usr/bin/find

What E-Mailing does it do?

By default, cron does local system mailing. It does not automatically send emails to external addresses (like Gmail or Outlook) unless your operating system has a mail server (like Postfix) explicitly configured and hooked up to an external account.

Instead, here is how cron's email mechanism actually works:

  1. Local System Inbox: Whenever a cron job produces text output (either standard print statements or error messages), cron tries to mail that output to the local user account that ran the job (e.g., your username).
  2. Where it goes: It drops the message into a local mailbox file on your machine, typically located at /var/mail/your-username or /var/spool/mail/your-username.
  3. Most of the time, people ignore it: On a standard personal computer or cloud server where no mail transfer agent is installed, these emails just sit silently in that local file, or cron throws them away if it can't find a local mailer.

How to manage cron's output:

  • To completely shut off emails and output: This is what most people prefer for routine cleanup tasks like deleting old backups. You redirect everything to the void (/dev/null) directly in your crontab line: 
0 2 * * * find /path/to/backup -type f -mtime +30 -delete >/dev/null 2>&1
  • To catch errors only: If you do want to know if something goes wrong, you can let it output errors, or write a tiny script that only prints or notifies you if a command fails.

Unless you explicitly configure a tool like postfix or msmtp with an external SMTP relay, your cron jobs won't spam your personal email address.

1. Using Minutes Instead of Days

Yes, you can easily use minutes instead of days by swapping -mtime for -mmin.

For example, to delete files older than 60 minutes, you would use: 

find /path/to/backup -type f -mmin +60 -delete
  • +60: Older than 60 minutes
  • -60: Newer than (modified within) the last 60 minutes

2. What Happens if the Target Directory is Deleted or Moved?

If the directory specified in your find command stops existing (e.g., it was deleted or renamed), the command will fail gracefully and throw an error message, but it won't break your system.

  • In the Terminal: It will print an error like:

find: ‘/path/to/backup’: No such file or directory and exit with a non-zero status code.

  • In a Cron Job: Because cron executes this silently (if you appended >/dev/null 2>&1), it will fail quietly in the background without affecting anything else. The next time the cron job runs after you recreate or restore the folder, it will magically start working again.

Pro-Tip to make it bulletproof: If you want to prevent error messages or script crashes when a directory might not exist yet, you can wrap the command in a conditional check: 

[ -d "/path/to/backup" ] && find /path/to/backup -type f -mmin +60 -delete

This safely checks if the directory exists (-d) before attempting to run the find command.

What If The Calendar Day And Day Of The Week Conflict? Do They Cancel Each Other?

No, it doesn't register as void! Instead, traditional cron does something quite surprising: it treats them with an "OR" relationship rather than an "AND" relationship.

If you restrict both the day-of-the-month field and the day-of-the-week field (meaning you don't use an asterisk * for either), cron will run the job when either condition matches, not when both match.

How it behaves:

  • Example: 0 0 13 * 5 (which means: 12:00 AM on the 13th day of the month OR every Friday).
  • The Result: The job will run on every single Friday, plus every 13th of the month (even if that 13th falls on a Tuesday). It does not wait for a "Friday the 13th".

How to avoid this:

If you actually want a strict "AND" condition (e.g., only on Mondays that are also between the 1st and 7th), you leave one of the day fields as an asterisk * and handle the extra filtering logic inside your command script using an if statement.

More On Cron Syntax

Cron syntax follows a 5-field structure: Minute Hour Day-of-Month Month Day-of-Week. Here are uncommon, clever, or counterintuitive crontab patterns that go beyond standard daily or hourly jobs.

Standard Field Structure

┌───────────── minute (0 - 59)
│ ┌───────────── hour (0 - 23)
│ ┌─│───────────── day of month (1 - 31)
│ │ ┌─│───────────── month (1 - 12)
│ │ │ ┌─│───────────── day of week (0 - 6) (Sunday=0 or 7)
│ │ │ │ │
* * * * * command_to_execute

Unintuitive & Overlooked Syntax Patterns

  • 0 9 * 1-5 (Workdays Only)*
  • Runs at 9:00 AM every Monday through Friday. Using range dashes (1-5) avoids writing multiple individual lines for each weekday.
  • */15 9-17 * 1-5 (Business Hours Step Intervals)*
  • Runs every 15 minutes, but strictly between 9 AM and 5 PM on weekdays. Combines step values (/) with range limits.
  • 0 0 1,15 * * (Bi-Monthly Semi-Static Days)
  • Runs at midnight on the 1st and 15th of every month. Commas serve as discrete set matchers.
  • *0 12 1-7 1 (First Monday of the Month)
  • Runs at noon only on the first Monday of any month. The trick: day-of-month is restricted to 1–7, ensuring the Monday (1) fall within the first week.

The OR-Condition Edge Case (Crucial Footgun)

# CAUTION: Day-of-Month and Day-of-Week use OR logic, not AND
0 0 15 * 5
  • Why this trips people up: If both Day-of-Month and Day-of-Week are specified (and neither is *), standard cron executes if either condition is true. The line above runs on every Friday and on the 15th of every month, not just on Fridays that happen to fall on the 15th.
  • The Workaround (using shell logic): 
0 0 15 * * [ $(date +\%u) -eq 5 ] && /path/to/script.sh

*Shorthand Non-Standard @ Macros*

Most modern cron implementations (Vixie Cron, systemd timers, cronie) support built-in macros that replace the 5-column syntax entirely:

Macro Equivalent Syntax Execution Timing
@reboot N/A Runs once at system startup/boot
@yearly / @annually 0 0 1 1 * Jan 1st at midnight
@monthly 0 0 1 * * 1st of every month at midnight
@weekly 0 0 * * 0 Every Sunday at midnight
@daily / @midnight 0 0 * * * Every day at midnight
@hourly 0 * * * * First minute of every hour

Project - Cron Report to Slack

Here is the step-by-step process to delete the files, count how many were removed, and send a notification to Slack using a webhook and curl.

Step 1: Get a Slack Webhook URL

To post messages to Slack via curl, you need an Incoming Webhook URL.

  • Go to your Slack workspace settings (or ask your Slack administrator) to create a custom app or enable Incoming Webhooks for a specific channel (e.g., #alerts or #pipeline-logs).
  • Once enabled, Slack will provide you with a unique Webhook URL.
  • Keep this URL handy; you’ll paste it into your script.

Step 2: Create a Bash Script

Create a new file anywhere safe in your user directory (for example, inside a scripts folder in your home directory), name it cleanup_backup.sh, and open it in your text editor: 

vim ~/cleanup_backup.sh

Paste the following script into it (remember to swap out the placeholder webhook URL with your actual Slack URL):

(Amend the WEBHOOK line) 

#!/bin/bash

# Configuration
TARGET_DIR=<your path>
# remove dots
W.E.B.H.O.O.K_U.R.L=<your_web_hool_URL>

# 1. Count how many files match the criteria before deleting
FILE_COUNT=$(find "$TARGET_DIR" -type f -mtime +1 | wc -l)

# 2. Only proceed if there are actually files to delete
if [ "$FILE_COUNT" -gt 0 ]; then
    # Delete the files
    find "$TARGET_DIR" -type f -mtime +1 -delete

    # 3. Format the message for Slack
    MESSAGE="🧹 *Backup Cleanup Report*\nDeleted *\$FILE_COUNT* old file(s) from \`$TARGET_DIR\`."

    # 4. Send the payload via curl
    curl -X POST -H 'Content-type: application/json' \
         --data "{\"text\": \"$MESSAGE\"}" \
         "$WEBHOOK_URL"
fi

Save and close the file (Ctrl+O, Enter, then Ctrl+X in nano).

Step 3: Make the Script Executable

Before cron can run your script, you need to give it execution permissions in the terminal: 

chmod +x ~/cleanup_backup.sh

(Optional: You can test the script right now by running ~/cleanup_backup.sh in your terminal to see if it successfully cleans files and pings Slack!)

Step 4: Update Your Crontab

Now, open your crontab (crontab -e) and replace your old line with a simple call to your new script: 

# Run the backup cleanup script Mon-Sat at 3:00 AM
0 3 * * 1-6 /home/yourusername/cleanup_backup.sh

(Make sure to replace /home/yourusername/ with your actual home directory path, which you can find by typing echo $HOME in your terminal).

Why this approach is great:

  • Clean & Maintainable: Your crontab stays simple and readable.
  • Smart Conditions: The if [ "$FILE_COUNT" -gt 0 ] check ensures that Slack isn't spammed with notifications on days when there are no files to delete.
  • Extensible: If you later decide you want to log these events to a local text file or add error handling, you can easily add it right into your .sh script!
