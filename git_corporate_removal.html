Git - Removing Repos

QUESTION

If I have a git repo stored on a corporate server, and I work and push updates to my remote repo on GitHub, what security considerations should I be aware of? For example, I have a git repo with a tool I've been developing, but I'm about to leave the company. Should I be doing something to prevent the repo (local and remote on Github) being connected anymore?

ANSWER FROM GEMINI

When you develop a tool on corporate infrastructure but push to a remote repository on GitHub (especially a personal one), leaving the company introduces critical legal, data privacy, and access-control security considerations. Here is exactly what you need to be aware of and the concrete steps you should take to safely disconnect everything before you leave.

1. The Big Legal & Compliance Considerations

  • Intellectual Property (IP): If you wrote this tool on a corporate server, on company time, or using company resources, the company legally owns that code in almost all jurisdictions under "work-for-hire" rules. Pushing proprietary corporate code to a personal GitHub account can be flagged by corporate data loss prevention (DLP) software and could lead to legal action or termination.
  • Secrets and Credentials: Ensure no corporate API keys, SSH keys, database passwords, or internal server IPs are hardcoded anywhere in the Git commit history. Even if a file is deleted in a later commit, the secret remains visible in the repository's history. [1, 2]

2. Action Plan: How to Disconnect the Repository

If the tool is legitimately yours (or you have explicit, written permission from management to take it with you), you must break the link between your personal GitHub account and the corporate machine to prevent the company from accessing your GitHub or vice-versa after you leave.

Step A: Disconnect the Local Corporate Repo from GitHub

You want to ensure that anyone who takes over your corporate computer/server cannot push to or pull from your remote GitHub repository. To completely sever the connection, remove the remote tracking information:

  • Navigate to your project folder on the corporate server.
  • Run this command to remove the connection to GitHub (usually named origin): 
git remote rm origin
  • Verify it is disconnected by running git remote -v. It should return completely blank.
  • (Optional but Recommended) If you are leaving the machine entirely, delete the local folder or the hidden .git metadata folder to prevent your local commit history from being read: 
rm -rf .git

Step B: Revoke Access Tokens and Keys on GitHub

Even if you remove the remote URL locally, the corporate server might still hold your authentication tokens or SSH keys in the system's global cache or keychains.

  • If you used SSH: Go to your GitHub Settings > SSH and GPG Keys. Look for the SSH key tied to your corporate machine and click Delete.
  • If you used HTTPS with a Personal Access Token (PAT): Go to your GitHub Settings > Developer Settings > Personal Access Tokens. Locate the token you used on the corporate server and Revoke it immediately.

Step C: Check Corporate GitHub Organization Permissions

  • Leave the Corporate Org: If your remote repository is hosted under a corporate GitHub Organization (rather than your personal profile) and you were added as a collaborator, you should proactively remove yourself. Go to your GitHub Settings > Repositories, find the repository under "Code, planning, and automation", and click Leave. [5]
  • Transfer Ownership: If the repo is on your personal GitHub but belongs to the company, transfer the repository ownership to a manager's corporate GitHub account via the repository's Settings > Danger Zone tab before your account access is cut off. [6, 7]

Personal Repo

Since the repository lives on your personal GitHub account, you are in full control of the remote copy, but you face the highest risk regarding Intellectual Property (IP) compliance and unauthorized access after you leave.

Because it is on your personal account, corporate IT systems cannot automatically revoke access to it. You must take proactive steps right now to secure both your account and the corporate server.

Step 1: Mitigate Legal & IP Risks Immediately

If corporate IT, legal, or security audits discover a repository on a personal GitHub account containing code developed on a corporate server, it can trigger strict Data Loss Prevention (DLP) flags.

  • Make the Repo Private: If the repository is currently public, change it to Private immediately via Settings > Danger Zone > Change visibility. If it contains any company-specific logic, internal project names, or proprietary code, keeping it public after you leave is a massive liability.
  • Audit the Commit History for Secrets: Ensure no corporate credentials, internal domain names, or private API keys exist in the Git history. Remember, simply deleting a file in a new commit does not erase it from Git history. If secrets are found, you will need to use a tool like git-filter-repo or BFG Repo-Cleaner to purge them completely.

Step 2: Sever the Connection on the Corporate Server

You must ensure that whoever inherits your corporate server or machine cannot pull your private code down, push malicious code up to your profile, or view your personal GitHub details.

Run these commands inside the repository folder on the corporate server:

  • Remove the Remote: Delete the link pointing to your personal GitHub. 
git remote rm origin
  • Clear Global Git Configs: Ensure your personal email and name aren't stamped on global configurations for future users of that server profile. 
git config --global --unset user.name
  • Delete the Local Repo (If allowed): If the company doesn't need the code on that server, wipe the folder entirely. If they do need the code but you just want to disconnect your personal Git metadata, delete the hidden Git history folder: 
rm -rf .git

Step 3: Clean Up Credentials in GitHub Settings

Even after deleting the local connection, your corporate machine may still have cached authentication credentials. You must invalidate them from the GitHub side.

  • Revoke SSH Keys: Go to your personal GitHub Settings > SSH and GPG keys. Identify and delete the public key that belongs to your corporate machine.
  • Revoke Personal Access Tokens (PATs): If you authenticated via HTTPS, go to Settings > Developer Settings > Personal Access Tokens (Tokens classic or Fine-grained). Revoke the token you generated for that server.
  • Check Active Sessions: Go to Settings > Sessions. Look through the active web and device sessions. If you ever logged into the GitHub web interface from that corporate machine or a corporate VNC/RDP session, click Revoke on those devices.

Revoking the Local SSH Keys

You should not delete your entire .ssh directory. Doing so could break your connection to other servers, lose your configurations, and delete keys that have nothing to do with GitHub.

Instead, you should only remove the specific keys and configurations associated with your personal GitHub account.

Here is how to safely clean up your .ssh directory without breaking anything else:

1. Identify and Delete Only the GitHub Key Files

Look inside your .ssh directory to find the specific key pair you used for GitHub.

  • Run ls -la ~/.ssh to view your keys.
  • Look for files typically named id_rsa, id_ed25519, github_rsa, or similar.
  • If you have a key dedicated to GitHub (or if you used your main key for GitHub and no longer need it for any corporate servers), delete both the private key and the public (.pub) file: 
rm ~/.ssh/id_ed25519_github
rm ~/.ssh/id_ed25519_github.pub

2. Clean Up Your SSH Config File

If you set up a custom routing rule for GitHub, it will be stored inside the config file.

  • Open the file in a text editor: nano ~/.ssh/config
  • Look for a block of text that looks like this: 
Host github.com
   HostName github.com
   User git
   IdentityFile ~/.ssh/id_ed25519_github
  • Delete that specific block, save the file, and exit. ===

3. Clear the Active SSH Agent Cache

Even after deleting the files, the running background system process (ssh-agent) might still hold the key in your active login session's memory.

  • To completely flush all cached keys from your active terminal memory, run: 
ssh-add -D

4. Remove GitHub from known_hosts (Optional)

Your .ssh/known_hosts file logs the fingerprint of every server you connect to. While keeping it is harmless, you can remove GitHub's fingerprint to be thorough: 

ssh-keygen -R github.com

By targeting only the GitHub-specific entries, your corporate server remains fully functional for your team while ensuring your personal GitHub identity is completely erased from the machine.

Credentials

Once you finish cleaning up these SSH files, there other personal configuration files (like global .gitconfig credentials) you may want to double-check before you hand over the machine.

To completely wipe your personal credentials and identity from the Git configuration on that corporate machine, you need to clean up two places: the Git Global Configuration and the System Credential Manager (which caches HTTPS tokens).

Here is how to safely clear both.

Step 1: Clear Git Global Configuration

Git stores your default name, email, and credential preferences in a hidden file called ~/.gitconfig in your home directory.

  • Run these commands to completely unset your personal identification: 
git config --global --unset user.name
  • If you want to check if any other personal configurations are left behind, open the file to inspect it: 
vim ~/.gitconfig
  • Look for and manually delete any remaining lines referencing your personal GitHub, custom aliases, or private configurations. Save and exit (Ctrl+O, Enter, Ctrl+X).

Step 2: Clear the Cached HTTPS Tokens (Credential Manager)

If you ever connected to your personal GitHub using HTTPS (typing your username and a Personal Access Token), the machine cached that token in the OS credential helper so you wouldn't have to type it every time.

Depending on the operating system of your corporate machine, use the appropriate method below to erase it:

If the corporate machine is a Mac (macOS):

macOS saves these tokens securely inside the system Keychain app.

  • Run this command to tell Git to explicitly erase your github.com credentials from the Keychain: 
echo "url=https://github.com" | git credential-osxkeychain erase
  • To be absolutely sure, open the Keychain Access app via Spotlight (Cmd + Space), search for "github.com", right-click any matching Internet Password entries, and select Delete.

If the corporate machine is a Linux Server:

Linux often uses a plaintext cache or a built-in manager.

  • Force Git to clear its stored credentials: 
echo "url=https://github.com" | git credential reject
  • If you were using the basic "store" helper, it saved your token in plain text. Wipe that file completely by running: 
rm -f ~/.git-credentials

Step 3: Clear Your Shell History (Highly Recommended)

If you ever typed your GitHub Personal Access Token or sensitive commands directly into the terminal, they might be saved in your command history file.

  • To clear your current terminal session history and save the blank slate, run: 
history -c && history -w
  • (Optional) To erase your entire past history file completely: 
rm -f ~/.bash_history ~/.zsh_history

Once these steps are finished alongside your SSH cleanup, your personal GitHub identity will be completely detached and erased from the corporate system.
