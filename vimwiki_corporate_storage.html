Storing Vimwiki Away from .snapshot Directories

To avoid getting backed up via .snapshot directories on corporate systems:

Move the Data to a True Local Directory

• Move your vimwiki directories to the physical computer's local hard drive—usually under /var/tmp/, or a local scratch space like /scratch/. • Network snapshots only happen on network-mounted shares.

The /tmp directory is a standard temporary workspace found on Linux, macOS, and other Unix-like operating systems. It is a shared scratchpad where the operating system, running applications, and users can write temporary data that is only needed for a short period. It is not permanent.

An alternative is the /var/tmp/ directory. Not permanent, but less volatile for often used files.

If You Must Use Temporary Directories

If you have no choice but to use system temporary directories, use /var/tmp instead of /tmp.

Feature /tmp /var/tmp
Bypasses Network Snapshots? Yes (Lives locally) Yes (Lives locally)
Survives a Reboot? ❌ No (Wiped instantly) Yes (Persistent)
Automatic Cleanup? Cleared every 10 days (or on boot) Cleared only if unaccessed for 30+ days

Since your network home directory might be where the snapshots are happening, moving the actual folder to /var/tmp ensures the physical files sit safely on your machine's local hard drive. A symlink in your home folder can just act as a lightweight pointer (consuming zero snapshot space).

Here is the exact step-by-step process to set this up safely without losing your notes:

Step 1: Move your existing notes to /var/tmp

First, copy your entire existing Vimwiki folder to the local persistent temporary directory. Replace vimwiki with the actual name of your folder if it is capitalized or different: 

cp -r ~/vimwiki /var/tmp/vimwiki

Tip: Using cp instead of mv first ensures you have a safety backup in case you make a typo in the next steps.

rsync Alternative

rsync is the best tool for this because it handles directory structures cleanly and allows you to explicitly ignore specific files and folders.

By default, standard copy commands like cp -r or an unconfigured rsync will get stuck in an infinite loop or throw errors if they try to copy the virtual .snapshot directory.

The Exact rsync Command

To copy your wiki folder to /var/tmp while completely ignoring the .snapshot directory, run this command: 

rsync -av --exclude='.snapshot/' ~/vimwiki/ /var/tmp/vimwiki/

Breakdown of the command flags:

  • -a (archive mode): This is critical. It preserves your file permissions, modification times, symlinks, and ownership exactly as they are.
  • -v (verbose): This prints the files on your screen as they copy so you can watch the progress.
  • --exclude='.snapshot/': This tells rsync to completely skip over any directory named .snapshot encountered during the transfer.
  • The trailing slashes (/): Placing a slash at the end of both paths (~/vimwiki/ and /var/tmp/vimwiki/) tells rsync to copy the contents of the source folder into the contents of the destination folder, avoiding nesting a folder inside a folder (like /var/tmp/vimwiki/vimwiki).

Step 2: Verify the files copied correctly

Check that your notes are intact inside the new local directory: 

ls -la /var/tmp/vimwiki

Step 3: Delete the original network folder

Now that your files are safe in /var/tmp, delete the original folder from your network home directory so the snapshot engine stops tracking changes to it: 

rm -rf ~/vimwiki

Step 4: Create the Symlink

Create the symbolic link pointing from your home directory to the new local path: 

ln -s /var/tmp/vimwiki ~/vimwiki

Step 5: Test it

Verify the link works by listing your home directory folder. It should seamlessly show your notes: 

ls -la ~/vimwiki

When you open Vim and trigger your Vimwiki shortcut, Vim will follow the symlink and read/write directly to /var/tmp/vimwiki without realizing anything has changed.

⚠️ Two Crucial Risks to Keep in Mind

While this perfectly solves your snapshot issue, you must look out for these two caveats:

  • The 30-Day Cleanup Rule: Most corporate Linux environments run a background cleanup script (systemd-tmpfiles-clean). By default, it automatically deletes files in /var/tmp that haven't been modified or accessed in 30 days. If you go on a month-long vacation or don't open your wiki for a few weeks, the system might wipe your notes. To prevent this, just touch the folder occasionally, or add touch /var/tmp/vimwiki to your ~/.bashrc or ~/.zshrc file so it updates every time you open a terminal.
  • Hardware Dependency: Because /var/tmp lives on that specific physical machine's hard drive, you will only be able to access your Vimwiki when using that exact workstation. If you SSH into your corporate network from a different machine or a backup server, your ~/vimwiki symlink will look "broken" because that second machine won't have your files on its local /var/tmp drive.

If you want to completely eliminate the risk of the 30-day auto-deletion, we can check if you have a non-temporary local folder. To find one, what is the output if you run:

  • df -h (This will show us all local vs. network hard drives mounted to your machine)

Location

The /var/tmp directory is physically local to the specific machine you are currently logged into, but it is globally shared across all users who have access to that machine. Here is exactly how it breaks down across your criteria:

Where is it? (It is Local)

It lives on your computer's local, physical hard drive (usually under the root / partition). Because it does not live on the corporate storage servers, it is completely invisible to the network snapshot engines.

Is it shared across users? (Yes, Globally)

Any user logged into that specific workstation or server can see and write to /var/tmp.

  • Permissions: By default, /var/tmp has a special permission bit set called the "sticky bit" (visible as a t at the end of its permissions, like drwxrwxrwt).
  • What the sticky bit means: While any user can create files inside /var/tmp, users cannot delete, modify, or rename files owned by someone else.

What this means for your Vimwiki plan:

Because it is shared, your rsync command will create a folder structure like /var/tmp/vimwiki/ that belongs strictly to your username.

  • Other users on that machine will be able to see the filenames of your notes if they browse /var/tmp.
  • However, because of default Linux file permissions (umask), they generally will not be able to read or modify the contents of your notes unless your files are explicitly set to be world-readable.

Secure it further (Optional)

If your Vimwiki contains sensitive or private notes and you want to ensure no other local users can even peer into the directory, you can lock down the local folder immediately after running your rsync command by restricting its permissions: 

chmod 700 /var/tmp/vimwiki

This ensures that only you (and the system root administrator) have permission to read, write, or list the files inside that directory.o

Checking the System

Here is how to check your default file sharing privacy (umask) and verify who else is logging into your machine to ensure your local Vimwiki repository is completely secure.

Suggestion 1: Check Your File Sharing Privacy (umask)

By default, when you or a program creates a new file or directory, Linux applies a mask called a umask to restrict permissions. Let's see how private your system is by default.

Open your terminal and simply type:

umask

Interpret the 4-digit numeric output:

  • 0022 or 0002 (Standard corporate default): This means files are readable by other users. If this is your output, other users on the machine can read your Vimwiki notes in /var/tmp unless you explicitly lock it down.
  • 0077 (Secure default): This means all new files are strictly private to you.

🔒 How to secure it right now:

Regardless of your default umask, you can completely lock down your local Vimwiki folder so that only you (and root) can see it. Run this command: 

chmod 700 /var/tmp/vimwiki

If you run ls -ld /var/tmp/vimwiki, the permissions should now look like drwx------, meaning read, write, and execute permissions belong exclusively to you.

Suggestion 2: See Who Else Logs Into This Specific Machine

Because /var/tmp is shared among local users, it's good to know exactly who you are sharing the computer with. You can check this using two different commands:

A. See who is logged in right now

Type the following command to see a live list of active users, what terminal they are using, and when they logged in: 

who

(If you only see your own username listed, you are the only one actively using the machine right now).

B. See who has logged in recently (Login History)

Type this command to view the historical log of all recent user logins on this system: 

last | head -n 20

This prints the last 20 login sessions. If you see names other than your own, those are the coworkers or system administrators who share this local hard drive space with you.

Summary Checklist to Finish Your Move Safely

Now that your rsync is done and you know how to secure it, here is the final sequence of commands to execute to wrap everything up: 

# 1.Lock down the local directory so other users can't read your notes
chmod 700 /var/tmp/vimwiki
# 2. Delete the original folder from the network share (stops snapshots)
rm -rf ~/vimwiki
# 3. Create the symlink shortcut
ln -s /var/tmp/vimwiki ~/vimwiki

Setting a 'Touch' command with Crontab

A crontab cronjob is the perfect, bulletproof way to touch this directory to preserve.

Using cron ensures that even if you don't log into the machine or open a terminal for weeks (like during a vacation), the system will automatically update the timestamps on your Vimwiki folder, completely immune to the 30-day /var/tmp cleanup policy.

Here is how to set it up in less than a minute:

Step 1: Open your user crontab

Open your personal cron configuration file in editing mode by running: 

crontab -e

Note: If it asks you to choose an editor, pick your favorite, like Vim or Nano.

Step 2: Add the automated touch rule

Scroll to the very bottom of the file and paste the following line on its own blank line: 

0 0 * * * touch /var/tmp/vimwiki

How this specific rule works:

  • 0 0 * * *: This tells cron to run the command every single day at midnight (12:00 AM).
  • touch /var/tmp/vimwiki: This updates the "last modified/accessed" timestamp of your folder to the current time without altering any of the actual files inside it. Because the timestamp updates daily, it will never trigger the 30-day automatic deletion threshold.

Step 3: Save and Exit

  • If you are using Vim: Press Esc, type :wq, and hit Enter.
  • If you are using Nano: Press Ctrl + O to save, hit Enter, then Ctrl + X to exit.

Once saved, your terminal will output a success message: crontab: installing new crontab.

💡 Extra Safety Step (Optional)

If you want to be 100% certain that your files are safe, you can instruct the cron job to update both the main folder and all notes inside it by adding the recursive flag (-c is not needed, just touch the folder and files).

Changing the command to touch -h /var/tmp/vimwiki /var/tmp/vimwiki/* ensures the entire structure stays fresh.

However, just touching the top-level folder touch /var/tmp/vimwiki is usually more than enough to stop system cleanup daemons from deleting the directory.
