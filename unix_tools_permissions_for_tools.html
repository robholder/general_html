Security - Permissions on Directories but Allowing Tool Symlinks

How it works conceptually

  1. Directory Read (r) vs. Execute (x):
  2. Read permission on a directory lets a user list its contents (i.e., run ls).
  3. Execute (or traverse) permission lets a user access a known file or subdirectory inside it, even if they cannot list the directory.
  4. The Magic Trick: If a user does not have r (read) permission on a directory, but does have x (execute) permission, they cannot browse, list, or see what else lives in that directory. However, if they know the exact path or follow a symlink directly to a file inside it, they can run or read that specific file.

Step-by-Step Implementation

Assume you have a private directory /home/secret_admin/utils/ and you want to share a specific utility called cool_tool with everyone, without letting them browse the utils/ folder.

1. Set the directory permissions

Restrict the directory so that "others" (everyone else) have execute-only access (--x), while you retain full control (rwx): 

chmod 711 /home/secret_admin/utils
  • *Owner (7 / rwx):* You can read, write, and browse.
  • *Group (1 / --x):* (Optional group settings).
  • *Others (1 / --x):* Can traverse through it, but cannot ls (read) it.

2. Set the utility file permissions

Make sure the utility itself has read and execute permissions for everyone: 

chmod 755 /home/secret_admin/utils/cool_tool

3. Create a global symlink

Place a symbolic link to the utility in a system-wide directory that is already in everyone’s $PATH (like /usr/local/bin): 

ln -s /home/secret_admin/utils/cool_tool /usr/local/bin/cool_tool

What users experience:

  • If a standard user tries to browse your folder: 
$ ls /home/secret_admin/utils/
ls: cannot open directory '/home/secret_admin/utils/': Permission denied

(They are completely blocked from seeing what else is in there.)

  • If a standard user tries to run the utility: 
$ cool_tool

(It executes successfully! Because the kernel traverses /home/secret_admin/utils using the execute bit and hits the target file directly.)

Git Protection

To secure your repository while allowing users to execute the tool, you should set the .git directory permissions to *700* (owner-only access: rwx------).

Why this matters (How 711 works)

A 711 permission on your parent development directory means:

  • Blocked: Other users cannot list the contents (ls) of the directory.
  • Allowed: Other users can traverse through it if they know the exact path to a file inside (which is why your symlinked tool works).

However, if your .git directory has default permissions (usually 755), any user who guesses or knows the path .git/ can traverse into it. Because .git contains your entire source code history, commit logs, branches, and potentially sensitive config data, a default permission leaves your source code exposed.

Recommended Steps

  1. *Lock down the .git directory:* 
chmod 700 .git

This ensures that even though others can traverse the parent 711 directory, they are explicitly blocked from entering or reading anything inside the .git folder unless they are the owner.

  1. Ensure git internal files are secure:

Git usually creates files inside .git with restricted permissions automatically, but running a recursive lock on .git doesn't hurt to be safe: 

chmod -R og-rwx .git

That command is a quick and effective way to lock down your entire .git directory so that only you (the owner) can access it, blocking everyone else completely.

The command breaks down piece by piece as follows:

  • chmod: The command used to change file and directory permissions in Unix-like systems.
  • -R (Recursive): Tells the command to apply this permission change to the .git directory and everything inside it (all subdirectories, commit logs, config files, and object databases).
  • og: Stands for *O*thers (anyone else on the system) and *G*roup (other users who share your primary user group).
  • -: Means to remove or revoke permissions.
  • rwx: Stands for Read, Write, and Execute.
  • .git: The target folder being modified.

Put It All Together

When you run chmod -R og-rwx .git, you are telling the system: "Take the .git folder and every file/folder inside it, and strip away all read, write, and execute permissions for others and the group."

This leaves the permissions at 700 (owner has full rwx, while group and others have ---). It ensures that even if someone manages to traverse into your development directory, they cannot peek into your version control history or source code database.

Best Practice Alternative

While chmod 711 on the dev folder and 700 on .git works as a quick fix, running shared production tools straight out of an active development/git directory is risky.

If possible, consider a cleaner deployment model:

  • Build/Compile/Copy the stable tool to a dedicated deployment directory (e.g., /usr/local/bin/my_tool or a shared production path) rather than symlinking directly into a live dev workspace.
  • This completely separates your source code and .git history from the tools regular users need to touch.

Other Directories

Understanding Your Current Permissions

Your default folders (Documents, Downloads, etc.) currently show drwxr-xr-x (755). This means the owner has full read, write, and execute permissions, while group members and others have read and execute permissions.

While others cannot modify or delete your files (since there is no write permission for others), they can list the contents of those folders and read any files inside them, provided they have local access to your machine. On a multi-user machine or a shared development environment, this is a privacy leak.

Should You Tighten These Settings?

Yes, for folders containing personal documents, credentials, or code, it is best practice to restrict access to only your user account.

  • The Ideal Setting: chmod 700 (drwx------) or chmod -R og-rwx for private directories. This ensures that only you can read, write, or enter those directories.
  • Why it matters: Even if a corporate machine is technically "yours," IT support, auditing tools, or shared accounts (if applicable) might exist. Restricting standard local users from snooping in your Documents is standard security hygiene. 
chmod 700 <file_or_dir>

...or, better for recursion (see reason below - where all files get executable treatment) 

chmod -R og-rwx <file_or_dir>

See below why a recursive chmod -R 700 <file_or_directory> isn't ideal.

chmod 700 vs. chmod -R og-rwx

While both restrict access so that only you can access the files, they work differently in scope and application:

  • chmod 700:
    • Applies to a single file or directory specified in the command.
    • It sets the exact permission mode (User gets rwx, Group gets ---, Others gets ---). It does not affect files inside the directory unless specified.
  • chmod -R og-rwx
    • The -R flag makes it recursive, meaning it applies the change to the target directory and every file and subdirectory nested inside it.
    • og-rwx means "remove (-) others' and group's read, write, and execute permissions," while leaving your user permissions untouched.

If you are securing a folder with existing files inside it (like Documents or Downloads), ch-R is typically what you want so that the files inside are protected as well, not just the folder shell.

The Syntax and Meaning of og-rwx

It is completely normal to find symbolic permissions intimidating—they look like a secret code!

However, once you learn the underlying "grammar," it actually reads almost like a plain English sentence.

Think of a symbolic command as a three-part sentence: [Who] [Action] [Permission].

1. Decoding the Formula (og-rwx)

When you look at og-rwx, you can break it down into three distinct blocks:

  • og (Who): Specifies the target audience.
    • u = User (the owner)
    • g = Group
    • o = Others (everyone else)
    • a = All (combines u, g, and o)
  • (Action): What you want to do to those permissions.
    • + = Add permission
    • - = Remove permission
    • = = Set exact permission (overriding everything else)
  • rwx (Permissions): The specific rights being altered.
    • r = Read
    • w = Write
    • x = Execute

So, og-rwx translates directly to: "For others and group, minus (remove) read, write, and execute."

2. Why It Is Smarter for Recursive Commands (-R)

The main reason symbolic mode is superior for recursive tasks comes down to how Linux handles files versus directories.

  • The Octal Flaw (700): If you run chmod -R 700, you are applying an absolute numeric value to everything. This means directories get rwx------ (correct), but every single file (text documents, scripts, configuration files) also gets forced to rwx------ (making ordinary documents executable programs).
  • The Symbolic Precision (og-rwx): This is a surgical adjustment. It tells the system: "Leave the owner's custom permissions alone, but strip the group and others of everything." Files remain non-executable, and directories retain their necessary execution bits.

3. Other Handy Examples

Once you get comfortable with this pattern, you can construct other useful rules easily:

  • u+x: Add execute permission just for yourself (great for making a shell script executable).
  • go-w: Remove write permissions for group and others (a classic security setting for shared project files so nobody else can tamper with them).
  • a+r: Make a file readable by everyone.

Is It Ok To Mess With Permissions On A Corporate System?

Generally, yes, tightening your local folder permissions is completely fine and often encouraged by security teams. However, keep a few operational caveats in mind:

  • Corporate Backups: Some automated enterprise backup agents run with elevated privileges (root/system) to back up your machine. These tools bypass standard file permissions, so tightening them won't break your backups.
  • Shared Workflows: If you intentionally collaborate with other developers locally on the same machine by dropping files into shared directories, restricting permissions will break that workflow.
  • Company Policy: Always defer to internal IT security policies if your company explicitly mandates specific compliance configurations.

How to Verify If You Are the Only User

To check if other human user accounts exist on your system, you can inspect the user database.

  • On Linux: Run awk -F: '\(3 >= 1000 && \)1 != "nobody" {print $1}' /etc/passwd to list standard user accounts. If only your username appears, you are the sole human user.
  • On macOS: Run dscl . -list /Users and look through the list, ignoring system accounts (usually starting with an underscore).
  • Quick active check: Run who to see who is currently logged into the machine.

On my corporate account I get zabbix & apache listed

These are created automatically by software applications, not other human users.

Here is what those two specific accounts are for:

  • apache: This is used by the Apache HTTP Server, one of the most popular web servers in the world. It runs background web services under its own restricted account for security isolation.
  • zabbix: This belongs to Zabbix, an enterprise-grade IT infrastructure and network monitoring software used to track system performance, disk space, and services.

Why did they show up?

Normally, system accounts are given lower User IDs (UIDs below 1000) so they stay hidden from standard user filters. However, depending on how they were installed or your specific Linux distribution, some software packages assign them UIDs of 1000 or higher, which is why your awk command caught them.

You are the only human user on the machine. These accounts are completely normal and are just running background tools.
