Security - Permissions on Directories but Allowing Tool Symlinks

How it works conceptually

  1. Directory Read (r) vs. Execute (x):
  2. Read permission on a directory lets a user list its contents (i.e., run ls).
  3. Execute (or traverse) permission lets a user access a known file or subdirectory inside it, even if they cannot list the directory.
  4. The Magic Trick: If a user does not have r (read) permission on a directory, but does have x (execute) permission, they cannot browse, list, or see what else lives in that directory. However, if they know the exact path or follow a symlink directly to a file inside it, they can run or read that specific file.

Step-by-Step Implementation

Assume you have a private directory /home/secret_admin/utils/ and you want to share a specific utility called cool_tool with everyone, without letting them browse the utils/ folder.

1. Set the directory permissions

Restrict the directory so that "others" (everyone else) have execute-only access (--x), while you retain full control (rwx): 

chmod 711 /home/secret_admin/utils
  • *Owner (7 / rwx):* You can read, write, and browse.
  • *Group (1 / --x):* (Optional group settings).
  • *Others (1 / --x):* Can traverse through it, but cannot ls (read) it.

2. Set the utility file permissions

Make sure the utility itself has read and execute permissions for everyone: 

chmod 755 /home/secret_admin/utils/cool_tool

3. Create a global symlink

Place a symbolic link to the utility in a system-wide directory that is already in everyone’s $PATH (like /usr/local/bin): 

ln -s /home/secret_admin/utils/cool_tool /usr/local/bin/cool_tool

What users experience:

  • If a standard user tries to browse your folder: 
$ ls /home/secret_admin/utils/
ls: cannot open directory '/home/secret_admin/utils/': Permission denied

(They are completely blocked from seeing what else is in there.)

  • If a standard user tries to run the utility: 
$ cool_tool

(It executes successfully! Because the kernel traverses /home/secret_admin/utils using the execute bit and hits the target file directly.)

Git Protection

To secure your repository while allowing users to execute the tool, you should set the .git directory permissions to *700* (owner-only access: rwx------).

Why this matters (How 711 works)

A 711 permission on your parent development directory means:

  • Blocked: Other users cannot list the contents (ls) of the directory.
  • Allowed: Other users can traverse through it if they know the exact path to a file inside (which is why your symlinked tool works).

However, if your .git directory has default permissions (usually 755), any user who guesses or knows the path .git/ can traverse into it. Because .git contains your entire source code history, commit logs, branches, and potentially sensitive config data, a default permission leaves your source code exposed.

Recommended Steps

  1. *Lock down the .git directory:* 
chmod 700 .git

This ensures that even though others can traverse the parent 711 directory, they are explicitly blocked from entering or reading anything inside the .git folder unless they are the owner.

  1. Ensure git internal files are secure:

Git usually creates files inside .git with restricted permissions automatically, but running a recursive lock on .git doesn't hurt to be safe: 

chmod -R og-rwx .git

Best Practice Alternative

While chmod 711 on the dev folder and 700 on .git works as a quick fix, running shared production tools straight out of an active development/git directory is risky.

If possible, consider a cleaner deployment model:

  • Build/Compile/Copy the stable tool to a dedicated deployment directory (e.g., /usr/local/bin/my_tool or a shared production path) rather than symlinking directly into a live dev workspace.
  • This completely separates your source code and .git history from the tools regular users need to touch.
