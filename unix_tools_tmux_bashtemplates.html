Tmux - Bash Templates

I wanted to have some kind of template to create and launch Tmux Sessions for specified shots (a template for common and often used consoles).

Bash Scripting

You can write a simple Bash script that creates a session, sets up windows and panes, changes directories, and names everything dynamically using arguments passed to the script.

Create a script named tshot: 

#!/bin/bash

# Check if a session identifier was provided (e.g., "01/05" or "ProjectA")
if [ -z "$1" ]; then
    echo "Usage: $0 <session-name>"
    exit 1
end

SESSION_NAME="$1"
# Optional: Define a base directory based on your directory structure
BASE_DIR="$HOME/projects" 

# 1. Create a new detached tmux session with the first window named 'Shots'
tmux new-session -d -s "$SESSION_NAME" -n "Shots"

# 2. In the 'Shots' window, split it into two panes
# By default, split-window splits vertically. Let's make it horizontal (-h) or vertical.
tmux split-window -v -t "$SESSION_NAME:Shots"

# Navigate panes to specific directories if needed
# tmux send-keys -t "$SESSION_NAME:Shots.0" "cd $BASE_DIR/$SESSION_NAME && clear" C-m
# tmux send-keys -t "$SESSION_NAME:Shots.1" "cd $BASE_DIR/$SESSION_NAME/logs && clear" C-m

# 3. Create the second window named 'Utility' with a single pane
tmux new-window -t "$SESSION_NAME" -n "Utility"
# tmux send-keys -t "$SESSION_NAME:Utility" "cd $BASE_DIR/$SESSION_NAME && clear" C-m

# 4. Attach to the newly created session
tmux attach-session -t "$SESSION_NAME"

How to use it:

  • Make it executable: chmod +x tshot
  • Run it with your variable: ./tshot "01-05"

QUESTION

Before I try the bash approach, is this compatible with both Bash and Zsh?

ANSWER

Yes, this is fully compatible with both Bash and Zsh.

Since the script itself is executed by the system shell specified in the shebang line (#!/bin/bash), it doesn't matter whether your interactive terminal uses Bash or Zsh—the script will run the exact same way.

A Quick Tip for Zsh Users

If your session names or directory structures include special characters or if you decide to pass arguments with slashes (like 01/05), Zsh handles pattern matching and expansion slightly differently than Bash.

To ensure your script plays nicely when you run it from a Zsh terminal, just make sure you wrap your arguments in quotes when calling the script: 

./tshot "01/05"

QUESTION

Is it possible to run commands in the windows/panes during the setup script?

I'd like to give a sequence number and a shot number and have the session be created, the windows named as planned (which should be generic apart form the session name), then call on utilities to navigate and set the env for each window based on the two numbers given as args with running the Tmux setup script.

For example: 

tshot 100 37

(Note: usually the args would be numbers, but they could be strings.)

ANSWER

Yes, absolutely! You can easily accept multiple arguments (like a sequence number and shot number) and pass automated commands down into specific windows and panes upon creation using tmux send-keys.

Here is how you can update your tshot script to handle two arguments (e.g., sequence and shot) and execute setup commands or environment variables inside each pane automatically:

The Enhanced Setup Script (tshot)

#!/bin/bash

# Ensure both sequence and shot numbers are provided
if [ -z "$1" ] || [ -z "$2" ]; then
    echo "Usage: $0 <sequence-number> <shot-number>"
    echo "Example: $0 100 37"
    exit 1
fi

SEQ="$1"
SHOT="$2"
SESSION_NAME="${SEQ}_${SHOT}" # Creates session name like "100_37"

# Define your directory structure template using the variables
# Adjust this path pattern to match how your directories are actually laid out
PROJECT_DIR="/path/to/your/shows/seq_$SEQ/shot_$SHOT"

# -----------------------------------------------------------------
# 1. Create session and first window ('Shots' with 2 panes)
# -----------------------------------------------------------------
tmux new-session -d -s "$SESSION_NAME" -n "Shots"

# Split the 'Shots' window vertically into two panes (Pane 0 top, Pane 1 bottom)
tmux split-window -v -t "$SESSION_NAME:Shots"

# Configure Pane 0 (e.g., Main work pane: nav to directory & set environment)
tmux send-keys -t "$SESSION_NAME:Shots.0" "cd $PROJECT_DIR" C-m
tmux send-keys -t "$SESSION_NAME:Shots.0" "echo 'Loaded Sequence $SEQ, Shot $SHOT'" C-m
# Add your custom environment command here, e.g.:
# tmux send-keys -t "$SESSION_NAME:Shots.0" "my_custom_env_tool --seq $SEQ --shot $SHOT" C-m

# Configure Pane 1 (e.g., Secondary pane, like logs or playback tools)
tmux send-keys -t "$SESSION_NAME:Shots.1" "cd $PROJECT_DIR" C-m
tmux send-keys -t "$SESSION_NAME:Shots.1" "echo 'Utility / Logs Pane'" C-m


# -----------------------------------------------------------------
# 2. Create the second window ('Utility' with a single pane)
# -----------------------------------------------------------------
tmux new-window -t "$SESSION_NAME" -n "Utility"

# Configure the Utility window pane
tmux send-keys -t "$SESSION_NAME:Utility.0" "cd $PROJECT_DIR" C-m
tmux send-keys -t "$SESSION_NAME:Utility.0" "htop" C-m # Example: auto-launching a utility


# -----------------------------------------------------------------
# 3. Finalize
# -----------------------------------------------------------------
# Select the first window and primary pane before attaching
tmux select-window -t "$SESSION_NAME:Shots"
tmux select-pane -t "$SESSION_NAME:Shots.0"

# Attach to the session
tmux attach-session -t "$SESSION_NAME"

How to use it:

  • Save the code into a file called tshot.
  • Give it execution permissions: 
chmod +x tshot

Run it using your custom numbers: 

./tshot 100 37

What happens under the hood:

  • C-m: This stands for "Control-M", which is the equivalent of pressing Enter in Tmux. It tells the pane to execute whatever string was just sent to it.
  • Target Specifiers ($SESSION_NAME:Shots.0): Tmux reads these identifiers precisely to mean Session -> Window Name -> Pane Index (0 for top/left, 1 for bottom/right), allowing you to control completely different tasks in different areas simultaneously.

ANSWER

Yes, absolutely. Since nh behaves like a standard command line utility accepting arguments, you can pass it directly via tmux send-keys into any pane you want.

Assuming nh is a registered function, alias, or executable script available in your shell environment, your script can type it out and hit enter automatically.

Important Caveat for Aliases & Functions:

If nh is defined as a Bash/Zsh alias or a shell function (rather than an independent executable script stored in your ＄PATH), newly spawned Tmux panes might not recognize it initially. Shells spawned inside Tmux default to non-interactive or fresh environments where local aliases aren't always auto-imported.

To ensure nh is always found:

  • Best approach: Turn nh into a small standalone script (e.g., an executable file named nh placed somewhere in your system or local ~/bin path).
  • Alternative approach: If it must remain a shell function/alias, make sure it's defined inside your ~/.bashrc or ~/.zshrc, and your Tmux template sources it first: 
tmux send-keys -t "$SESSION_NAME:Shots.0" "source ~/.bashrc && nh $SEQ $SHOT" C-m

Allowing for just first letter for Flavor

# Extract only the first character and convert to lowercase just in case
FLAVOR="${3:0:1}"
FLAVOR="${FLAVOR,,}"

Those two lines use built-in Bash features to safely clean and normalize whatever the user types for the flavor argument so that variations like H, Hou, or Houdini all map correctly.

Here is a breakdown of how each line works:

Extracting the first character: FLAVOR="${3:0:1}"

This uses Bash parameter expansion to slice a substring out of the third positional argument (＄3).

  • 3: Refers to the third argument passed to the script (e.g., houdini).
  • :0: Tells Bash to start slicing at index 0 (the very beginning of the string).
  • :1: Tells Bash to take a length of 1 character.

So, whether the user types hou, Houdini, h, or even something like heavy, this line grabs just the h (or H).

Converting to lowercase: FLAVOR"${FLAVOR,,}"

This uses Bash case-modification operator to ensure the letter is strictly lowercase.

  • ,,: This specific operator tells Bash to convert all characters in the variable to lowercase. (If it were uppercase like ^^, it would convert everything to uppercase).

So, if a user accidentally types an uppercase letter like H or N, this line instantly turns it into h or n.

Why do both?

By combining them, your script becomes completely foolproof. No matter if the user enters h, hou, HOUDINI, or NuKe, the script reliably reduces it down to a clean lowercase h or n, making your if/elif statements evaluate successfully every time.

Clashing Session Names

If the script tries to create a session name that already exists (for example, you already have 100_37_houdini running and you run the script for it again), Tmux will abort the creation and throw an error, causing your script to fail right out of the gate.

Specifically, Tmux prints an error message to your terminal like: 

duplicate session: 100_37_houdini

Because the script errors out at the tmux new-session line, it won't run any of the window/pane creation logic, and it won't execute your final tmux attach-session command.

How to handle this (The Smart Fix)

Depending on what you actually want to happen when a session already exists, you have two options:

Option 1: Just jump straight into the existing session (Most common)

If a session for that shot is already open, you probably don't want to recreate it from scratch—you just want to attach to the one that's already running.

You can update the session creation line in your script to use Tmux’s -A (attach) flag. If the session already exists, -A tells Tmux to skip creating a new one and just attach to it; if it doesn't exist, it creates it normally: 

# Instead of: tmux new-session -d -s "$SESSION_NAME" ...
# Use -Ad (Attach + Detached initialization, which safely handles existing sessions):
tmux new-session -Ad -s "$SESSION_NAME" -n "houdini"

(Combined with -d, it ensures the session initializes safely in the background if it's new, and then your final tmux attach-session at the bottom of the script will drop you right into it).

Option 2: Throw a clean warning message

If you want your script to explicitly warn you instead of crashing ungracefully, you can check if the session exists using tmux has-session before running your block: 

if tmux has-session -t "$SESSION_NAME" 2>/dev/null; then
    echo "Session '$SESSION_NAME' already exists! Attaching..."
    tmux attach-session -t "$SESSION_NAME"
    exit 0
fi

Avoid Mirroring the Same Tmux Session

The unfortunate thing is this re-attaches to an existing Tmux session if it is already attached and creates a 'mirror' in the current Terminal.

If you are running the script from a brand new OS terminal window, which launches a brand new Tmux client attached to the existing session, it results in two separate terminal windows mirroring the exact same thing.

Here is the underlying technical reality: Tmux only knows about text terminals (TTYs), it has no idea what graphical OS window or desktop workspace your terminal emulator lives in. Because of this, a shell script running inside a terminal cannot natively command your operating system (Linux/macOS) to "find the GUI window on workspace 2 and bring it to the front."

However, depending on what you want to happen, you have two great ways to handle this:

Option 1: "Steal" the session into your current terminal (-d)

If you want to stop spawning a second terminal view and instead pull the session directly into your current window (while automatically disconnecting it from the old one), you can add the -d (detach) flag to your attach command: 

# This detaches the session from any other terminal and brings it here
tmux attach-session -d -t "$SESSION_NAME"

What happens: The old terminal window will disconnect/exit, and the session will be safely transferred to your current terminal window.

Option 2: Detect if it's running and block duplicates

If you want the script to realize "Hey, this session is already open somewhere" and prevent you from accidentally spawning a messy duplicate view, you can check if the session already has an active client using tmux list-clients: 

# Check if the session is already actively attached to a client
if tmux list-clients -t "$SESSION_NAME" 2>/dev/null | grep -q .; then
    echo "Session '$SESSION_NAME' is already open in another window!"
    echo "Please switch to that window or use 'tmux attach -d -t $SESSION_NAME' to steal it."
    exit 1
fi

Danger in Stealing a Session?

Stealing a session will not harm a background processes.

The Technical Reality of tmux attach -d

When you use the -d flag to "steal" or re-attach a session, Tmux only disconnects the client view (the terminal UI window). It does not touch, restart, or kill any processes running inside the panes. The Tmux server keeps everything alive in the background. If you had a render or a long script running, it would keep right on going without interruption.

Why the Warning Approach is Still Better

Even though your background processes are safe from the -d flag, your workflow peace-of-mind is not!

Getting suddenly yanked out of a session because someone (or a stray script) attached to it from another terminal window can be deeply disruptive—especially if you're actively typing or looking at something on another monitor. Choosing the warning route is definitely the safer choice for a clean, predictable pipeline.
