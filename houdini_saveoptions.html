Houdini Save/Backup Options

The "Make Numbered Backup" option in SideFX Houdini creates an incremental backup copy of your current .hip file in a dedicated subfolder before overwriting the main file with your new changes.

How It Works

  • Action: When you press save (Ctrl+S), Houdini looks for an existing file on disk.
  • Copying: It moves a copy of that old file into a local backup folder next to your project.
  • Renaming: It renames the copy using an incremental number pattern (such as filename_bak1.hip, filename_bak2.hip).
  • Saving: It then updates your main working file with your current progress.

Set Preferences

To ensure your custom folder rules are never bypassed, verify that your software preferences match these exact parameters:

  • Navigate to:
    • Edit > Preferences > Save / Loading.
  • Save Method: Set this to Overwriting Current File.
    • Why: If this is accidentally changed to "Increment File Name", Houdini generates a brand new v008.hip scene file every single time you hit save. It will bypass your custom backup folders completely.
  • Numbered Backups: Ensure this checkbox is Explicitly Enabled (Checked).
    • Why: This toggle is the master lock. If this is turned off, Houdini ignores all your custom HOUDINI_BACKUP_DIR rules and overwrites your main working script raw.

The Save and Save_As Difference

If you are currently working in comp_v0002.hip and you choose File > Save As to change the name to comp_v0003.hip, no backup files are created at all during that action.

Houdini's "Make Numbered Backup" system only triggers when an existing file on disk is about to be overwritten. Because comp_v0003.hip does not exist yet, Houdini creates it fresh, leaving your backup directories completely untouched.

The exact state of your files on disk, their names, and their contents will break down as follows:

In the Main Project Directory

  • comp_v0002.hip
    • Content: It stays frozen exactly at the state of your last manual save of v0002.
    • Any un-saved tweaks you made right before clicking "Save As" are not inside this file.
  • comp_v0003.hip
    • Content: This is your new active working file.
    • It contains your most current live progress, including all the unsaved node changes you made right up to the exact millisecond you clicked "Save As".

In the Backup Directories

  • The backup/ folder:
    • Contains history from your previous manual <Ctrl> + S actions while working on v0002.
    • No new backup file is added here during the "Save As" command.
  • The backup/ folder:
    • Houdini will not generate a backup file until the next time you are inside v0003 and press <Ctrl> + S to overwrite it.

Summary of What Triggers What

  • <Ctrl> + S (Save): Overwrites an existing file -> Triggers a backup entry.
  • <Ctrl> + <Shift> + S (Save As): Establishes a brand-new file -> Skips the backup engine entirely.

Key Settings & Location

  • Default Folder: Houdini automatically creates a folder named backup inside your scene's directory ($HIP/backup).
  • Customization: You can adjust how these files are named or where they go using environment variables like HOUDINI_BACKUP_DIR in your configuration.
  • Difference: This applies to your regular manual saves or auto-saves depending on how you configure your global preferences.

Houdini's Save and Autosave Strategy

By default, Houdini handles and names auto-saves slightly differently than your manual saves.

If you use the default interface preferences, manual saves get labeled with a _bak suffix, while background auto-saves get stamped with an _auto suffix. However, if you are using highly customized directory patterns (as described later on this page), your auto-saves will actually bypass your file-specific subfolders unless you configure a separate matching variable.

How Auto-Saves Interact with Configurations Described Below

  • The Same Directory: By default, auto-saves use the exact same directory (backup) or target variable (existing path/directory) that you defined in HOUDINI_BACKUP_DIR (but only if it exists!). They will successfully place themselves into backup or your explicitly defined folder path.

The Fix: Mirroring the Settings for Auto-Saves

To force your backups and auto-saves to a name or path use these two variables with either hard names, variable understandable by Houdini, or subdirectories using /. (These subdirectories - unlike the HOUDINI_BACKUP_DIR - will be created by Houdini if they don't exist):

  • Locate the file: Open your file explorer and navigate to your user preferences directory based on your operating system:
    • Windows: C:\Users\<YourUsername>\Documents\houdiniXX.X\houdini.env
    • Mac: ~/Library/Preferences/houdini/XX.X/houdini.env
    • Linux: ~/houdiniXX.X/houdini.env 
      HOUDINI_BACKUP_FILENAME = "backups_$USER/\$BASENAME_bak\$N.hip"
HOUDINI_AUTOSAVE_FILENAME = "autosaves_$USER/\$BASENAME_auto\$N.hip"

Open your houdini.env file and update your variables block to include this matching definition: 

# ---------------------------------------------
# DYNAMIC PER-FILE BACKUP PIPELINE
# ---------------------------------------------
# Leave this unset so it natively targets your open project directory ($HIP)
# Houdini will create a 'backup' directory if this is left blank (a subdirectory
# of the $HIP location. If a hard path is entered (which must exist), backup is
# not used, and the hard path is used directly.
#HOUDINI_BACKUP_DIR = "<explicit_path_which_MUST_exist>"
#HOUDINI_BACKUP_DIR = "/someserver/work/houdini/myshot_100/houdini/mybackup"

# 1. Control manual save backups; note the subdirectory here:
HOUDINI_BACKUP_FILENAME = "backups_$USER/\$BASENAME_bak\$N.hip"

# 2. Control auto-saves; note the subdirectory here: 
HOUDINI_AUTOSAVE_FILENAME = "autosaves_$USER/\$BASENAME_auto\$N.hip"

# 3. Restrict history clutter per file
HOUDINI_MAX_BACKUP_FILES = 20
  • ＄USER -> username
  • ＄BASENAME -> open file's name
  • ＄N -> Houdini's backup or auto-save number

Why This Is highly Optimized

By keeping the structures split:

  • Clear Context: You can instantly tell if a file was a deliberate manual checkpoint (_bak1) or a background timer snap (_auto1) just by looking at the filename.
  • Clean Organization: Both manual files and auto-save files will with the exact same ＄BASENAME filename. Your main directories will remain completely clean and organized by USERNAME.
  • Using the settings above, you will have two clearly defined directories, with the username baked in to separate users.

Houdini's Crash Saves

Houdini’s automatic Crash Saves operate on a completely different subsystem than manual backups or timed auto-saves. They are designed as a last-resort recovery mechanism when the application encounters a fatal error, memory overflow, or segmentation fault.

The Triggering Event

  • Backups & Auto-Saves: These run smoothly while Houdini is stable. They cleanly serialize your node configurations into files.
  • Crash Saves: These trigger exclusively when the core program is actively dying. When Houdini detects a fatal failure, it intercepts the operating system's kill command, pauses its own shutdown for a split second, and attempts to scrape your active RAM into an emergency file before the process terminates.

Complete Separation of Directories

Crash files intentionally bypass your project’s ＄HIP space, date directories, and custom folders. If your network drive or project folder loses connection (a frequent cause of crashes), Houdini needs a local directory to dump the recovery data.

  • The Path: Crash saves are written to your local operating system's standard temporary directory token (＄TEMP or ＄TMP).
    • Windows default: C:\Users\<YourUsername>\AppData\Local\Temp\
    • Linux/Mac default: /tmp/houdini_temp/

Naming Format Differences

Crash files disregard your naming rules entirely. Because the asset environment variable strings may be corrupted during a crash, Houdini uses a hardcoded naming convention: 

crash.<YourFileName>_base.<ProcessID>.hip
  • Example: crash.pyro_simulation_v01_base.14824.hip
  • The numeric string at the end is a randomized Operating System Process ID. This prevents a new crash from accidentally overwriting an older recovery asset.

No File Volume Restrictions

Your custom HOUDINI_MAX_BACKUP_FILES = 10 rule does not apply to crash recoveries. Houdini will never automatically delete older crash files to clean up space. They accumulate over time in your local temporary folder until your operating system runs a disk cleanup or you delete them manually.

How to Access a Crash Save

Modern versions of the software feature a native recovery hook. If you restart Houdini immediately after an abnormal termination, a popup dialog box will appear asking to restore your last session.

Alternatively, you can browse to the recovery files directly via File > Open Crash File or Open Crash Folder.

Editing Env Settings

Editing your user houdini.env configuration file is the best way to handle autosave numbers and limits.

How to Limit Backup Files Using houdini.env

  • Locate the file: Open your file explorer and navigate to your user preferences directory based on your operating system:
    • Windows: C:\Users\<YourUsername>\Documents\houdiniXX.X\houdini.env
    • Mac: ~/Library/Preferences/houdini/XX.X/houdini.env
    • Linux: ~/houdiniXX.X/houdini.env

(Note: Replace XX.X with your exact installed Houdini version.)

  • Open the file: Open houdini.env using any basic, raw plain-text software like Notepad, Gedit, TextEdit or Vim.
  • Add the variable: Scroll down to the very bottom of the document, create a new blank line, and type the following variable: 
HOUDINI_MAX_BACKUP_FILES = 10
  • Save and restart: Save your text file and restart Houdini.

Houdini will now look into your local scene $HIP/backup directory and automatically delete the oldest version whenever a new manual or auto-save file pushes the total count past your chosen limit.

Backup Directory

If you edit the HOUDINI_BACKUP_DIR and assign an alternative path, you must use an existing path. Houdini will not create this directory if it doesn't exist

AutoSave 'On' With Wrappers

You cannot use shell aliases or flags to force auto-save "On".

Houdini lacks a native command-line flag or global environment variable argument to switch this feature on. Terminal aliases (like naming a custom shortcut) only let you pass variables to the main execution file but won't trigger internal software parameters like auto-save.

Since you cannot modify the corporate wrappers, you can achieve this by dropping two tiny files directly into your local personal user preferences directory. Houdini scans your local directory right after the corporate wrapper loads.

The Local Directory Solution

Houdini natively looks for two built-in setup files upon launch: 123.cmd (runs when you launch Houdini empty) and 456.cmd (runs when you open an existing file).

  • Locate your local user directory: Go to your document folder where your preferences are stored:
    • Windows: C:\Users\<YourUsername>\Documents\houdiniXX.X\
    • Mac: ~/Library/Preferences/houdini/XX.X/
    • Linux: ~/houdiniXX.X/
  • Create a scripts folder: Inside that version folder, create a new folder named lowercase scripts (if one does not already exist).
  • Create the files: Inside the scripts folder, create a raw plain-text document.
  • Add the command: Type the following exact line inside it: 
autosave on
  • Save and Name: Save the file name as 123.cmd.
  • Duplicate it: Copy that file and rename the duplicate to 456.cmd.

How This Bypasses the Wrapper

When you launch your locked corporate wrapper, it prepares the studio pipeline environment variables and triggers the main executable. As soon as the application opens, it reads your local user documents folder to apply your UI settings. It will encounter your 123.cmd and 456.cmd files and immediately toggle auto-save to "On" behind the scenes, leaving your studio wrapper completely untouched.
