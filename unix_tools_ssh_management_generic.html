SSH - Generic

1. Generate and Load Keys

Prefer ed25519 for new keys; keep rsa or older keys only for legacy systems that require them.

Always set a passphrase on keys stored on a laptop. 

# Generate a new Ed25519 key
ssh-keygen -t ed25519 -C "<your-email@example.com>"

# Start ssh-agent (pick the line for your shell):
# Bash / Zsh / POSIX:
eval "$(ssh-agent -s)"
# tcsh / csh:
eval `ssh-agent -c`

# Load your private key (replace filename as needed)
ssh-add ~/.ssh/id_ed25519

# macOS modern (Sequoia / recent macOS) - store passphrase in Keychain:
ssh-add --apple-use-keychain ~/.ssh/id_ed25519

# macOS legacy (e.g., Mojave) - store passphrase in Keychain:
ssh-add -K ~/.ssh/id_ed25519

Add the public key to GitHub or the remote server: 

cat ~/.ssh/id_ed25519.pub
# Copy the full line (ssh-ed25519 AAAA... <comment>) into GitHub > Settings > SSH and GPG keys

2. Organizing ~/.ssh/config

OpenSSH reads ~/.ssh/config top to bottom. For most settings, the *first matching line* for a host applies, so put *specific hosts above broader patterns*, and put Host * *last*.

Strategy A: Simple Single-Key / Mac Keychain Setup

  • When to use: One personal machine, one primary key, and you want macOS Keychain integration.
  • Superseded by: Strategy B or C once you manage multiple keys, servers, or accounts. 
    # ~/.ssh/config (modern macOS)
Host github.com
  HostName github.com
  User git
  IdentityFile ~/.ssh/id_ed25519

Host *
  AddKeysToAgent yes
  UseKeychain yes

Strategy B: Multiple Accounts or Aliases (Recommended as Soon as You Have 2+ Keys)

  • When to use: Separate keys for personal vs. work/client accounts, or short nicknames for servers.
  • *Why it's better than Host * + IdentityFile:* Prevents SSH from trying the wrong key or hitting account lockouts on shared hostnames. 
    # ~/.ssh/config
# More specific aliases/hosts come FIRST

Host github-personal
  HostName github.com
  User git
  IdentityFile ~/.ssh/id_ed25519_personal
  IdentitiesOnly yes

Host my-server
  HostName 192.0.2.10
  User deploy
  IdentityFile ~/.ssh/id_ed25519_server
  IdentitiesOnly yes

# Broad fallback goes LAST
Host *
  AddKeysToAgent yes

Strategy C: Wildcard / Domain Patterns

  • When to use: Several hosts share a naming pattern or internal domain and use the same key or user.
  • Precedence note: Place above Host *, but below exact Host aliases that need exceptions. 
    Host *.internal.example.com
  User ops
  IdentityFile ~/.ssh/id_ed25519_ops

3. Test and Debug Connections

# Test GitHub authentication
ssh -T git@github.com
# Expected: "Hi <user>! You've successfully authenticated, but GitHub does not provide shell access."

# Clone over SSH (accept host fingerprint on first connect if verified)
git clone git@github.com:<user>/<repo>.git

# Inspect effective config for a target host without connecting
ssh -G github-personal | grep -E "hostname|user|identityfile|usekeychain|addkeystoagent"

4. Change or Verify Key Passphrase

Changing a passphrase updates only the local private key file; your public key on GitHub or servers does not change. 

# Change (or remove by entering a blank new passphrase)
ssh-keygen -p -f ~/.ssh/id_ed25519

# Quick test without connecting to a remote host (prints public key if passphrase works)
ssh-keygen -y -f ~/.ssh/id_ed25519

# End-to-end test against a remote host
ssh -i ~/.ssh/id_ed25519 user@hostname

5. Machine-Specific & Historical Notes

  • M3 MacBook Pro (Sequoia): Uses ssh-add --apple-use-keychain and UseKeychain yes in ~/.ssh/config.
  • 2012 Intel MacBook Pro (Mojave): Uses ssh-add -K and UseKeychain yes. Ensure the file is at ~/.ssh/config (with the leading dot), not ~/ssh/config.
  • Linux (Bash vs. tcsh): Use eval "$(ssh-agent -s)" in Bash; use eval ssh-agent` or eval ssh-agent -c in tcsh`.
  • Pmount session log: Generated an ed25519 key with passphrase, started agent with eval ssh-agent -c (tcsh), loaded ~/.ssh/id_ed25519_pm, added ~/.ssh/id_ed25519_pm.pub to GitHub, and cloned the repo over SSH.

Strategy D: Multiple GitHub Accounts

  • When to use: Separate keys for personal and work/client GitHub accounts on the same machine.
  • Why it works: Distinct Host aliases point to HostName github.com with explicit keys and IdentitiesOnly yes. 
    # ~/.ssh/config

# Default / personal GitHub account
Host github.com
  HostName github.com
  User git
  IdentityFile ~/.ssh/id_ed25519_personal
  IdentitiesOnly yes

# Work / secondary GitHub account alias
Host github.com-work
  HostName github.com
  User git
  IdentityFile ~/.ssh/id_ed25519_work
  IdentitiesOnly yes

When cloning or updating a repo for the work account, point the remote at the github.com-work alias instead of github.com: 

# Clone using the work alias
git clone git@github.com-work:<work-org-or-user>/<repo>.git

# Or switch an existing repo's remote URL
git remote set-url origin git@github.com-work:<work-org-or-user>/<repo>.git

# Test the work alias
ssh -T git@github.com-work

Strategy E: Jump Host (Bastion) with ProxyJump

  • When to use: Reaching internal/private hosts through a bastion host in a single ssh or scp command.
  • Supersedes: Manual two-hop logins or older ProxyCommand workarounds for standard bastion hops. 
    # ~/.ssh/config

Host bastion
  HostName bastion.example.com
  User jumpuser
  IdentityFile ~/.ssh/id_ed25519_bastion
  IdentitiesOnly yes

Host app-internal
  HostName 10.20.30.40
  User appuser
  IdentityFile ~/.ssh/id_ed25519_internal
  IdentitiesOnly yes
  ProxyJump bastion

# Chain multiple hops if needed (left to right):
# ProxyJump jump1,jump2

    # Connects through `bastion` to `app-internal` automatically
ssh app-internal

6. Troubleshooting Common SSH Errors

Bad File Permissions (Permissions 0644 for private key are too open)

  • Cause: OpenSSH refuses private keys that are group- or world-readable, and strict setups check ~/.ssh permissions too.
  • Fix & verify: 
    chmod 700 ~/.ssh
chmod 600 ~/.ssh/id_*
chmod 644 ~/.ssh/*.pub
# Verify permissions (expect drwx------ for ~/.ssh and -rw------- for private keys):
ls -la ~/.ssh

Permission denied (publickey)

  • Cause: The server does not have your public key in ~/.ssh/authorized_keys (or GitHub account settings), or SSH tried a different key first.
  • Fix & verify: 
    # 1. Confirm which key SSH actually selects and negotiates
ssh -vT git@github.com 2>&1 | grep -E "Offering public key|Identity file|Authenticated"

# 2. Check that your public key matches what you uploaded to GitHub/server
cat ~/.ssh/id_ed25519.pub

# 3. For multi-account setups, confirm IdentitiesOnly is active in effective config
ssh -G github.com-work | grep -E "hostname|user|identityfile|identitiesonly"

SSH Agent Not Running or Key Not Loaded

  • Cause: A new terminal or shell session has no running ssh-agent environment variables, or the key was not added (or expired/reset after reboot).
  • Fix & verify: 
    # Start agent (Bash / Zsh) and list loaded key fingerprints
eval "$(ssh-agent -s)"
ssh-add ~/.ssh/id_ed25519
# Verify loaded keys (expect non-empty fingerprint list):
ssh-add -l
